Browser Use 插件设计方案评审

版本 3.1 · 用户态接入方案 · 2026-09-10

插件只做一件事：登录用户账号。Connector 给 Agent 开通浏览器能力；用户在私聊中批准本次任务。插件不绑定工作区，不绑定 Agent。

本文是目标产品与服务设计，不是 Demo 完成情况。具体接口、字段、代码差异见配套《实施设计》。文中的新增业务接口名称为设计约定，需后端评审后冻结。

1. 用户会怎样使用

1.1 首次使用：两件互不相关的事

插件登录。 安装插件后，在插件里点“登录”。插件打开统一登录页；网页已登录则单点登录直接完成，未登录则走正常登录／注册。完成后插件显示当前账号（头像、名称），并在后台保持在线。登录过程不出现工作区选择、不出现 Agent 选择、不打开 Connector 页面。 这和一个普通网站插件的登录体验相同。

给 Agent 开通能力。 在 OpenMAX 的“应用连接”里选择 Browser Use，选择有管理权限的 Agent，点击“连接”。系统为该 Agent 安装或启用 zylos-browser-channel，确认工具可用后显示“已开通”。这一步只关系到 Agent 有没有浏览器工具，与用户装了几个插件、插件是否登录无关。

插件不选 Agent、不选工作区、不输配对码、不领取浏览器专用绑定凭据；它只持有自己的用户会话，不复制网页 token。“应用连接”页面可以提示“未检测到插件，请先安装并登录”作为引导，但插件的登录入口不是这个页面。

两件事没有先后顺序要求。状态分别显示为“当前浏览器已登录并在线”和“Agent 工具已就绪”，不能合成一个含糊的“已连接”。

1.2 日常使用：只在对话里操作

用户在 Agent 私聊说“打开 1688，搜索儿童玩具”。需要浏览器时出现授权卡，点击“允许本次任务”后开始执行；不需要再打开插件批准。

Agent 按“观察 → 决策 → 操作 → 检查结果”循环，完成后清理工作标签，回原对话回复。等待登录时暂停，用户在网站处理后回对话点击“继续”。

同一插件可先后服务不同 Agent；每次只允许指定任务、指定 Agent 操作本次确认的浏览器。首期每个执行端同时一个任务，不提供跨设备选择、群聊共享或无人授权执行。

2. 服务各自负责什么

图中相同服务是同一个服务，不代表重复部署。入口网关与负载均衡略去；HTTPS 请求和 WSS 都经正式环境入口访问对应服务。

仓库／组件负责不负责
cws-fe应用连接入口（给 Agent 开通能力）、聊天授权卡、状态展示、当前插件核对不承担插件登录入口；不直接启动任务或发送 CDP
cws-core身份与 Agent 权限、工作区成员校验、HTTP 业务入口／BFF、WS 身份票据不逐条转发点击与截图
cws-connectBrowser 能力开通、任务授权与状态、期限、幂等回执、可靠事件不保存插件的用户登录 token，不执行浏览器动作
cws-comm普通聊天传输、Channel 安装控制帧；浏览器执行端在线、任务通知、指令与结果定向中转不把用户在线视为任务授权，不按用户广播页面数据
zylos-openmax接收平台聊天、确定性处理 Channel 安装命令、可信来源上下文、C4 续跑与回复适配不要求模型自己决定是否安装或判断授权是否有效
zylos-coreAgent 推理循环、C4／SQLite 消息投递；本机组件安装能力不保存平台浏览器任务授权的权威状态
zylos-browser-channelCLI、工具说明、任务连接、agent-browser 调度、受限 CDP 转发不承载独立聊天，不持有用户账号 token
zylos-browser-extension用户登录、后台在线、任务接单、工作标签、chrome.debugger、光标与清理不长期绑定 Agent、不负责模型决策
统一登录服务（Logto）OpenMAX 与插件共用的账号、登录／注册、单点登录不是 Browser 任务授权服务

命名说明： cws-comm 是通信服务；cws-common-go／Common Proto SDK 是共享代码和协议，不是一个要连过去的 WebSocket 服务。cws-core 是平台 Core，zylos-core 是 Agent OS。cws-agent-manager 管 Agent 实例生命周期，不放在本方案的 Channel 安装或每次浏览器执行链上。

3. 插件登录与在线

插件通过统一登录取得用户会话，向 cws-core 完成平台身份识别、申请浏览器用途的 WS 票据，再主动连接 cws-comm。Comm 记录“这个账号的这个浏览器执行端在线”。

登录的范围是用户账号本身，不是账号下的某个工作区。 一个用户可能属于多个工作区、和多个 Agent 私聊；插件登录一次，之后任何工作区里任何已开通的 Agent 发起任务，都可以经用户批准使用这个浏览器。工作区和 Agent 是任务的属性，在用户点击“允许”时由该条私聊决定，插件登录时不需要也不应该知道。

登录只证明你是谁，不授予 Agent 控制权。 空闲时不创建工作标签、不附加调试、不读取网页或截图。用户切换账号或退出插件时停止相关任务，断开旧执行端。

浏览器实例标识只是后台路由信息，不能当作登录凭据。现有聊天 WS 的组织级语义保持不变，浏览器用户态连接作为 Comm 内独立执行端入口扩展。

登录采用公开客户端流程，回调和扩展 ID 配套配置；可复用 Logto 的 Chrome 扩展 SDK。不是把网页 cookie/token 直接交给插件。Logto 扩展接入说明

4. Connector 给 Agent 开通能力

cws-fe → cws-core → cws-connect → cws-comm → zylos-openmax → zylos-core 组件管理 → zylos-browser-channel

  • Core 验证操作者有权管理目标 Agent；Connect 记录“开通中”并下发受控安装命令。
  • Comm 通过 Agent 已有 OpenMAX 连接投递命令，OpenMAX 适配器调用固定组件安装／启用逻辑，完成健康检查，再经 Core 回报 Connect。
  • Connect 收到对应请求的成功回执，才显示“已开通”；Comm 接受消息不等于安装成功。失败、离线、超时可查询和重试，不能显示虚假成功。

沿用现有 Channel 生命周期的开通方式，在应用连接页面提供 Browser Use 入口；这不是普通第三方 OAuth Connection，不派发浏览器用户凭据给 Agent。 已有合适版本时只需启用／核验，不应每次连接都强制升级。

安装能力可以由多个任务复用。它不建立“浏览器 A 永远归 Agent B”的关系，也不替任何用户批准任务。

5. 对话授权与执行

5.1 用户提出需求：创建卡片，同时预连接

私聊沿 cws-fe → cws-core → cws-comm → zylos-openmax → C4／SQLite → Agent 到达模型。浏览器工具请求经 Channel 的私有 broker 交给 OpenMAX，再经 Core 到 Connect。

Connect 核验真实来源消息、发起用户、会话中的 Agent 及 Browser 能力状态，建立待授权任务。授权卡的业务数据由 Connect 持有，Comm 通知原会话，FE 渲染。Agent 不是靠输出一段“已授权”文本取得权限。

此时任务还没有目标浏览器。Channel 可以提前建立任务级中转连接，但只能心跳与查询状态；不发送网页数据、CDP 或创建标签。插件未登录不妨碍解释需求，卡片需明确提示登录，不能把它误显示为可立即执行。

5.2 用户点击允许：只让这次任务开始

网页自动核对同一 profile 的插件登录身份和当前连接，得到本次确认；这是只读核对，不是网页通知插件直接开工。没有安装、未登录、离线或账号不一致时在原卡片提示，不转用另一个浏览器。

“允许”提交路径固定为 cws-fe → cws-core → cws-connect。 Connect 校验本次决定，向 Comm 确认并预占执行端，保存任务授权，再通过可靠事件通知插件准备。

插件回报 Ready 只表示接受本任务上下文，不表示已有页面。Connect 确认后，经 cws-comm → zylos-openmax → C4／SQLite 唤起 Agent。首条具体网址到达时才创建工作页，避免授权后停在空白页。

5.3 执行：观察与动作必须形成循环

执行主链是 Agent → zylos-browser-channel（含 agent-browser）→ cws-comm → 插件 → Chrome 工作标签。工具结果沿原路返回 Agent，不走普通聊天队列。

首次打开网址采用受限的建页指令；取得本任务的 CDP 目标后，后续定位、输入、点击和截图由 agent-browser 调度。截图要真正供模型查看，不能只返回路径就视为已观察。

Agent 与插件都主动连接 Comm，不要求 Agent 有公网 IP，也不向用户暴露 Agent 的入站端口。此方案首期只走平台中转，不维护公网直连第二套执行协议。

6. 工作标签与结束行为

你的页面不动；Agent 的临时页用完清理；明确要求保留的结果交还给你。

阶段行为
未授权／准备中不建工作页、不附加调试、不读取页面
实际执行在原对话页旁创建目标网址，加入彩色工作组；之后只操作任务自己的页面
需要登录／确认停止动作、解除调试与光标，保留“等待继续”组；在对话明确继续后恢复
结束／停止关闭临时页；保留结果移出分组并解除控制；不留下“已停止／已完成”分组

用户切换标签不改变任务目标。归属不明的页面不强制关闭，清理失败准确提示。正常最终回复在收尾确认后发送；“收尾不确定”不能描述为“已全部完成”。

7. 数据落在哪里

8. 异常、安全和验收

  • 重复点击只处理一次；迟到 Ready 不激活旧任务。断线恢复先对账，不重放不确定的点击、发送或提交。
  • 停止、退出账号、撤销使用权或过期后拒绝新动作，清理有上限；已提交给网站的动作不能承诺撤回。
  • 用户态只证明身份；任务还要验证真实发起人、会话使用权、工作区成员身份与 Agent。不能用模型自填的 user_id 决定控制谁。
  • Comm 将浏览器执行帧与普通聊天隔离，不向同用户其他聊天页或会话成员广播 DOM／截图。
  • 插件登录态不交给网页、内容脚本或 Agent；也不把网页数据、凭据写入普通运行日志。页面和截图会经平台到达 Agent，授权界面需说明这一点。
  • 用户自行处理密码、验证码、付款等敏感步骤；不承诺绕过网站限制或自动化所有网站。
  • Service worker 在线不是永不断线，需心跳、重连和权限失效上界。Chrome WebSocket 文档
  • Debugger API 的远程执行例外有范围，不等于任意热更新都可过审；发布前做权限、隐私与远程执行审核。Manifest V3 政策

验收重点：插件点“登录”只经过统一登录页，不出现工作区或 Agent 选择，也不打开 Connector 页面；登录后插件显示当前账号；开通有真实健康回执；同一插件可先后服务两个已开通 Agent；聊天只点一次允许；错误浏览器不被操作；准备无空白页；执行有观察循环；停止有效、结果清理正确；Agent 无公网入站地址时可完成全链路。

待评审确认：正式扩展登录客户端与回调、Browser 专用 Comm 协议、工作区映射规则、共享 Agent 使用范围、各阶段时限、结果页默认保留策略和数据保留期。建议首期只支持本人发起的私聊任务，不做自动跨设备路由。
