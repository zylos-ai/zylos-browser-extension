# NanoBrowser 借鉴分析：速度、消耗与执行体验

本次重点：用户反馈速度慢、消耗大、整体体验不顺畅。

分析日期：2026-09-16。基于工作区源码：Extension `a31989a`、Browser Remote `00afd30`、NanoBrowser `24a14b7`、Core `a5ab5d1`。这是代码分析与一次隔离的 CLI 输出验证，没有进行真实网站任务的性能对比，不能据此声称 NanoBrowser 整体更快，也不能给出提速比例。

## 建议方向

保留现有三项目分工，优先借鉴 NanoBrowser 的批量动作、精简观察、临时页面上下文和执行事件。先修正观察输出，再减少模型决策轮次和往返次数。是否需要专用浏览器 Agent，应由后续测量决定。

当前链路是：

```text
用户聊天 → Extension → Remote → C4 → Zylos Agent
工具调用 → browser.js → Remote /rpc → Extension → Chrome
结果返回 → Agent 决定下一步
```

C4 负责聊天投递，不是每次点击都重新经过 C4 排队。CLI 每次接受一个动作，但 Agent 已经可以在一次 shell 工具调用中顺序调用多个 CLI 命令；因此“一个动作必然对应一次模型调用”不成立。真正需要从轨迹测量的是：一个任务用了多少次模型决策、多少次 RPC、多少次页面观察。

## 已确认的具体问题

### 1. `observe` 的图片编码直接进入 CLI 输出

- Extension 的 `observe` 同时返回页面文本和 `screenshot.data`，图片采用 PNG。
- Remote CLI 仅在 `method === 'screenshot'` 时调用 `stashScreenshot()`。
- 因此 `observe` 的嵌套图片没有落盘转换，会随 JSON 直接写入 stdout。

证据位置：

- `utils/automation/executor.ts:972`
- `../zylos-browser-remote/scripts/browser.js:119`

隔离验证使用真实 CLI 源码、模拟 RPC 和文件系统，提供 1,024 字节合成图片：

| 调用 | stdout 字节数 | 包含原始 Base64 | 调用图片写文件逻辑 |
| --- | ---: | --- | --- |
| screenshot | 170 | 否 | 是 |
| observe | 1,538 | 是 | 否 |

验证未连接浏览器、未联网、未实际写入图片。这证明输出处理缺失；是否构成用户当前任务的主要消耗，仍取决于实际有没有调用 `observe` 以及运行时如何截断工具输出。

建议同时处理独立截图和观察中的截图，以 MIME 类型确定文件格式，向 Agent 返回路径和必要元数据。图片应通过图像工具读取，不能把 Base64 文本当作视觉输入。

### 2. 页面观察缺少按场景控制的输出预算

当前 `snapshot()` 逐 frame 读取完整 AX 树，按角色等条件输出，最多 600 个节点。`interactive=true` 能过滤输出，但仍执行完整 AX 树采集及敏感字段检查。默认值为 `false`，当前实现没有视口过滤、文本去重或变化摘要。

当前 `observe` 必定采集文本和截图；已有独立的纯文本 `snapshot`，所以并不是所有观察都必须截图。

证据位置：`utils/automation/page-actions.ts:164`、`utils/commands.ts:21`、`utils/automation/executor.ts:937`。

建议增加明确的观察模式：

- 操作：当前视口中的可操作元素、必要标签和少量上下文。
- 阅读：指定区域或正文，保留结果文本和表格内容。
- 视觉：需要理解布局、图标或文本不足时再附加截图。

输出应有字符或 token 预算，并明确标记截断。不能只保留按钮而丢掉搜索结果、表单提示和任务完成证据。敏感字段过滤必须保留。

### 3. 动作执行和下一次观察分开调用

当前点击、输入等动作通常返回小型结果；下一次等待、检查、快照由 Agent 另外发起。远端可能因此反复决策或往返。现有本地 `wait` 已支持具体条件及停止打断，可以复用。

证据位置：`utils/automation/page-actions.ts:461`、`utils/automation/executor.ts:576`、`utils/remote-commands.ts`。

建议增加声明式批量执行，让已确定的动作、等待条件和最后一次观察作为一个请求执行。例如已找到输入框后，依次填写、回车、等待结果区域、返回精简观察。等待条件必须来自已知页面信息，未知的结果布局需要重新观察后再决策。

## NanoBrowser 中值得借鉴的机制

| 机制 | 本地源码证据 | 对 Zylos 的适配 |
| --- | --- | --- |
| 一次模型输出包含多个动作 | `../nanobrowser/chrome-extension/src/background/agent/agents/navigator.ts:195`，`doMultiAction()` | Extension 提供有限批量动作；Remote 继续转发；Agent 决定批次内容 |
| 页面出现新元素时中断批次 | 同文件 `:391`，比较可点击元素路径哈希 | 页面跳转、弹窗、目标失效或影响下一步的变化发生时，返回已执行结果和新观察 |
| 当前页面状态作为临时上下文 | 同文件 `:199`，推理后移除状态消息，保留动作输出与必要结果 | 在可控的浏览器任务上下文中保留当前状态和短摘要，减少旧 DOM/截图累积 |
| 面向操作的页面表示 | `../nanobrowser/chrome-extension/public/buildDomTree.js`；`browser/dom/views.ts:212` | 借鉴视口筛选、可见性与交互判断、重复属性去除，继续利用现有 AX ref |
| 标记新出现的元素 | `../nanobrowser/chrome-extension/src/background/browser/page.ts:341` | 后续可提供变化摘要；首次观察和状态失效后必须返回完整基线 |
| 视觉输入可配置 | `../nanobrowser/chrome-extension/src/background/agent/types.ts:23` | 观察协议支持文本和视觉选项，由任务需要决定 |
| 结构化执行事件 | `../nanobrowser/chrome-extension/src/background/agent/event/` | 侧栏即时显示当前动作、等待原因、批次进度和失败原因 |

两点需要准确区分：NanoBrowser 标记新增元素并不等于每次只发送 DOM 差量；其截图开关也不等于已经实现智能、自动的视觉回退。差量观察和自动选择模式是 Zylos 可进一步设计的能力。

NanoBrowser 自己控制 LLM 消息列表，能主动删掉旧页面消息。Zylos 当前通过 Claude/Codex 运行时的 CLI 工具结果反馈，单纯修改 `SKILL.md` 无法删除已经进入运行时上下文的历史输出。第一阶段先压缩工具输出；只有基线显示历史上下文仍是主要瓶颈时，再考虑在服务器侧增加独立、可控的浏览器任务上下文。

## 不宜直接照搬的部分

- **每个动作后固定等待 1 秒。** `navigator.ts:430` 明确存在固定 sleep。应复用现有条件等待，对异步页面更新设置有上限的稳定等待。
- **照搬整套 Planner/Navigator。** 当前 NanoBrowser 执行器主要实例化这两个 Agent，Planner 周期性运行并确认完成。配置默认每 3 步规划一次；增加规划调用也增加耗时和消耗。Zylos 已有 Agent，先改善工具协议，避免重复规划。
- **把 LLM 和 Key 管理搬进插件。** NanoBrowser 在扩展内组织推理；Zylos 现有服务器 Agent 与插件执行器分工可以继续保留。批量执行不要求插件拥有模型。
- **整体替换 CDP 执行器。** 当前项目已有工作标签隔离、跨 frame 操作、过期 ref 检查、停止打断、请求去重及最终回复回执。观察与批处理改进可以建立在这些能力上。
- **仅靠缩短鼠标动画提速。** 当前轨迹目标时长约 100–320ms，实际还包含多次 CDP 调用。应测量累计开销；不能在没有数据时认定它是主要瓶颈。

批处理也不能直接复制 NanoBrowser 的异常处理：其循环捕获部分动作错误后可能继续执行。Zylos 第一版应默认遇错即停，明确已执行、失败、未执行的动作；超时或断线时不得自动重放整个批次。

## 建议实施顺序

| 阶段 | 具体交付 | 涉及项目 | 验收重点 |
| --- | --- | --- | --- |
| 1 | 修正 `observe` 图片输出，更新工具使用说明；记录代表任务基线 | Remote，必要时 Extension | 两种截图路径都不向 stdout 输出 Base64；实际任务可读取图片；记录耗时与输出体积 |
| 2 | 增加按操作/阅读/视觉需求选择的精简观察 | Extension + Remote 文档 | 相同任务观察体积下降，同时目标定位与结果读取成功率不下降 |
| 3 | 增加有限批量动作、条件等待、最终观察及中断返回 | Extension + Remote 文档 | 减少 RPC/决策轮次；页面变化和停止时正确中断；已完成动作不重复执行 |
| 4 | 推送动作和等待事件到侧栏 | Extension，跨端事件按实际需要扩展 Remote | 无需模型额外写进度消息，也能看见正在执行或等待的阶段 |
| 5 | 根据实测决定是否引入专用任务上下文 | Agent 集成层，必要时 Core | 比较额外模型调用开销、上下文节省与任务完成率 |

批量执行的建议协议边界：请求声明动作列表、总时限和观察选项；插件按顺序执行；返回每步状态、已执行数量、中断原因和最新观察。页面 ref 必须来自有效观察，批次执行期间继续检查任务归属及页面版本；不能跨导航复用旧 ref。是否新增元素只是变化信号之一，不能当作完整可靠性保证。

## 如何验证是否真的更快

使用相同模型与设置，对同一组任务做前后对比：搜索并读取结果、填写多个字段、筛选列表、滚动加载、弹窗/新标签页。区分稳定的本地测试页面与真实网站测试；记录浏览器初始状态，避免用缓存、登录差异解释代码收益。

每个任务分别记录：聊天到首个动作的时间、总耗时、模型决策轮次、RPC 次数与耗时、观察输出字节数、实际可获得的输入/输出 token、截图次数、重试次数和完成率。提供足够样本后再计算中位数和 p95，不能从少量演示任务外推。

Remote 已记录每个 RPC 的耗时（`../zylos-browser-remote/relay/agent-lane.js:101`）。先关联同一任务的现有日志，再补 Extension 的采集/动作阶段计时。模型耗时与 C4 排队需在对应层采集；没有真实轨迹前，不把模型、Relay 或 C4 中任何一层认定为主要瓶颈。
